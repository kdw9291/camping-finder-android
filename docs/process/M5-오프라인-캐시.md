## 2. 무엇을 캐시할 것인가 — 제일 먼저 정한 것

"오프라인 지원"이라는 말은 범위를 정하지 않으면 아무 뜻이 없다.
극단은 둘이었다.

| | 전량 프리페치 | 본 것만 캐시 |
|---|---|---|
| 3,082건 전부를 첫 실행에 내려받는다 | 오프라인이 완벽해진다 | 사용자가 요청하지 않은 수 MB 를 셀룰러로 받는다 |
| 오프라인 검색 | 된다 (필터 로직을 앱에 복제해야) | 안 된다 |
| 구현 난이도 | 높다 | 낮다 |

**본 것만 캐시하는 쪽을 골랐다.** 결정적인 이유는 용량이 아니라 아래 D1 이다.

## 3. 설계 결정

### D1. 필터 로직을 SQLite 에 복제하지 않는다 ★

조합 필터의 3-state 판정(있음 / 없음 / **미상**)은 서버에만 있다.
오프라인 검색을 지원하려면 이 규칙을 SQLite 쿼리로 다시 써야 한다.

**두 벌이 되면 반드시 어긋난다.** 어긋나는 순간 앱은 "전기 있는 곳"이라며 849곳을 조용히 빼먹는다.
그 실패를 막으려고 시작한 프로젝트에서 그 실패를 앱 안에 새로 만드는 셈이다.

그래서 오프라인에서는 **이미 받아 둔 검색의 결과만 재생한다.** 새 조건을 계산하지 않는다.
저장된 적 없는 조건을 걸면 결과가 나오지 않고, 화면은 그것을
"조건에 맞는 캠핑장이 없습니다"가 아니라 **"네트워크에 연결할 수 없고, 저장해 둔 정보도 없습니다"** 라고 말한다.

이 둘을 뭉뚱그리면 사용자는 있지도 않은 결론(그런 캠핑장은 없다)을 믿는다.
빈 값을 "없음"으로 바꿔 말하지 않는다는 이 앱의 원칙이 그대로 적용된 자리다.

### D2. 만료는 삭제가 아니라 **표시**다 ★

흔한 구현은 TTL 을 두고 만료된 캐시를 무효 처리한다.
여기서는 그렇게 하면 **산속에서 앱이 빈 화면이 된다.** 정확히 캐시가 필요한 순간에.

5일 전 정보는 정보가 없는 것보다 낫다. 대신 **5일 전 것이라고 말해 준다.**
판단은 사용자가 한다.

```
저장해 둔 정보입니다. 5일 전에 받은 것입니다.
```

"오프라인"만 알리고 나이를 감추는 것도 안 된다.
사용자가 알아야 하는 것은 연결 상태가 아니라 **눈앞의 운영시간이 언제 것인가**다.

배너에 경고색(error)을 쓰지 않은 것도 같은 판단이다. 이건 고장이 아니라 의도한 동작이다.
빨간 띠를 띄우면 사용자는 앱이 깨졌다고 읽고 멀쩡한 정보를 닫아 버린다.

### D3. 네트워크 우선, 캐시 폴백 (캐시 우선이 아니다)

캠핑장의 운영 상태(운영중/폐업)와 예약 URL 은 실제로 바뀐다.
**폐업한 곳으로 두 시간을 운전해 가는 것이 이 앱이 만들 수 있는 최악의 결과다.**
신호가 있으면 최신을 보여준다.

폴백은 `IOException` 에서만 일어난다. HTTP 4xx/5xx(`HttpException`)는 서버가 대답한 것이므로
그대로 던진다 — 잘못된 요청을 오래된 캐시로 덮으면 버그가 영원히 안 보인다.

### D4. 지도는 캐시하지 않는다

반경 검색 결과를 저장할 수 있지만 하지 않았다.
지도 타일은 네이버 서버에서 오고 오프라인에서는 받을 수 없다.
마커만 저장해 봐야 **빈 회색 배경 위에 점이 떠 있을 뿐**이다.

저장할 수 있다고 저장하는 것이 아니라, 저장해서 쓸모가 있을 때만 저장한다.

### D5. 마이그레이션을 쓰지 않는다

이 DB 는 서버 응답의 파생본이다. 스키마가 바뀌면 통째로 버리고 다시 받으면 된다.
백엔드에서 Supabase 를 공공데이터의 파생본으로 보고 EC2 를 무상태로 만든 것과 **같은 판단**이다.

```kotlin
.fallbackToDestructiveMigration(dropAllTables = true)
```

> ⚠️ **즐겨찾기가 들어오는 순간 이 줄을 지워야 한다.**
> 즐겨찾기는 파생본이 아니라 사용자가 만든 원본이다.
> 앱 업데이트 한 번에 조용히 사라지면 그건 데이터 손실이다.
> 그때 마이그레이션을 검증하려면 이전 버전 스키마 JSON 이 있어야 하므로,
> `room.schemaLocation` 을 **지금부터** 걸어 뒀다. 필요해진 다음에 남기기 시작하면 이미 늦는다.

### D6. Room 3.0 을 쓰지 않았다

Room 3.0(`androidx.room3:room3-runtime`)이 2026-03 에 나왔다. 그룹과 패키지가 통째로 바뀐
KMP 겨냥 재설계다. 쓰지 않은 이유:

- 이 앱은 안드로이드 전용이라 KMP 이점이 없다
- 새 코드베이스라 **stdlib 요구 버전이 AGP 9.3.1 내장 컴파일러(2.2.10, 메타데이터 2.3.0 까지)를 넘을 위험**이 있다.
  Coil 3.5.0 에서 정확히 같은 방식으로 당했다 (`libs.versions.toml` 주석 참고)
- 2.8.4 는 Kotlin 2.0/2.1 시절 산출물이라 이 제약과 확실히 맞는다

KGP 를 올릴 때 옮긴다. 패키지명이 바뀐 것이므로 이전은 치환 작업이다.

## 4. 스키마

```
campsite_summary   목록에 필요한 것. PK = contentId
search_result      "어떤 검색의 몇 번째였는가". PK = (queryKey, page, position)
campsite_detail    현장에서 실제로 열리는 것. LRU 200건
filter_options     JSON 한 덩이. 없으면 오프라인에서 필터 시트가 빈 화면
```

**요약과 순서를 분리한 이유** — 같은 캠핑장이 여러 검색에 걸려도 요약이 중복 저장되지 않는다.
페이지 교체는 `search_result` 만 지우므로 요약은 고아로 남고, 첫 페이지를 새로 받을 때 청소한다.

**PK 를 `contentId` 로 둔 이유** — 서버의 `id`(자체 시퀀스)는 서버 DB 를 재적재하면 바뀐다.
`contentId` 는 공공데이터의 식별자라 그대로다. 앱 캐시가 서버의 내부 사정에 흔들릴 이유가 없다.

**`distanceKm` 은 저장하지 않는다** — 반경 검색의 결과값이지 캠핑장의 속성이 아니다.
저장하면 다음에 다른 위치에서 꺼냈을 때 거짓말이 된다.

**LRU 기준이 `lastAccessedAt`(마지막으로 연 시각)인 이유** — 다음 주에 갈 캠핑장은
오래전에 받았더라도 계속 열어 본 곳이다. 받은 시각으로 지우면 정작 가려던 곳이 먼저 지워진다.

## 5. 함정

| 함정 | 내용 |
|---|---|
| **쿼리 키의 집합 순서** | `Set` 의 순회 순서는 보장되지 않는다. 정렬하지 않으면 같은 조건이 다른 키가 되어 캐시가 조용히 빗나간다. "가끔 오프라인에서 결과가 안 나오는" 재현 안 되는 버그 |
| **`includeUnknown` 을 키에서 빠뜨리기** | 이 값 하나로 결과가 849곳 달라진다 |
| **`ORDER BY position` 누락** | 조인 결과는 SQLite 가 임의 순서로 준다. 서버가 정렬한 순서가 무너져 목록이 매번 뒤바뀐다 |
| **페이지 교체 비원자성** | 지우고 넣는 사이에 앱이 죽으면 그 페이지만 빈 캐시가 남는다. 사용자는 그걸 "원래 결과가 그렇다"고 읽는다 → `@Transaction` |
| **컨버터를 구분자 문자열로** | 시설명에 콤마가 들어오면 조용히 깨진다. M0 에서 원본 데이터가 정확히 그렇게 배신했다 → JSON |
| **캐시 쓰기 실패로 화면을 막기** | 저장공간이 가득 찼다고 이미 손에 들어온 검색 결과를 못 보여주는 것은 말이 안 된다 → `runCatching` 으로 삼킴 |
| **고아 요약 누적** | 페이지 교체는 `search_result` 만 지운다. 안 치우면 캐시가 단조 증가 |

|---|---|

## 8. ★ 실패 기록

### 8.1 캐시 읽기가 터지면 앱이 오프라인에서 죽었다

리포지토리의 폴백이 이렇게 되어 있었다.

```kotlin
} catch (e: IOException) {
    readPageFromCache(queryKey, page) ?: throw e   // ← 여기서 또 터지면?
}
```

**캐시를 읽다 난 예외가 원본 IOException 을 밀어내고 위로 올라간다.**
사용자는 "네트워크에 연결할 수 없습니다" 대신 `SerializationException` 을 본다.
상세(`cache.detail`)와 필터(`decodeFromString`)도 같은 모양이었다 — 세 군데 전부.

**정확히 신호가 없는 그 순간에 앱이 낯선 예외로 죽는다.** 이 기능이 막으려고 만들어진 그 상황에서.

#### 어떻게 알아챘나

프롬프트가 "캐시 읽기 실패는 '캐시 없음'으로 흡수되어야 하는 것 아닌가" 라고 물었다.
테스트를 먼저 쓰고(페이크 DAO 의 읽기를 전부 터뜨린다) 돌렸더니 3건이 빨갛게 났다.
**코드를 읽어서가 아니라 테스트가 잡았다.**

#### 고친 방식

캐시는 서버 응답의 파생본이다(D5). **읽히지 않는 캐시는 캐시가 없는 것과 같다.**
그러니 흡수하는 것이 맞다 — 단, 조용히 사라지게 두지는 않는다.

```kotlin
private suspend fun <T> fallbackToCache(networkFailure: IOException, read: suspend () -> T?): T? =
    try { read() }
    catch (c: CancellationException) { throw c }
    catch (cacheFailure: Exception) { networkFailure.addSuppressed(cacheFailure); null }
```

`networkFailure` 의 타입을 **`IOException` 으로 좁게** 잡은 것이 뜻밖에 값을 했다 —
나중에 `catch (e: Exception)` 변이를 넣어 봤더니 **컴파일이 안 됐다.**
D3(HTTP 오류는 폴백 금지)를 타입이 지키고 있다.

### 8.2 `runCatching` 이 `CancellationException` 까지 삼키고 있었다

캐시 쓰기 세 군데가 `runCatching` 이었다. 그건 `Throwable` 을 전부 잡는다 —
**코루틴 취소까지.** 목록 화면은 새로고침할 때마다 이전 검색을 `searchJob?.cancel()` 하므로
실제로 지나가는 경로다. 취소를 삼키면 구조적 동시성이 깨진다.

`swallowCacheWriteFailure` 로 바꿔 취소만 다시 던진다. 의도(쓰기 실패는 무시)는 그대로다.

### 8.3 ★ `ORDER BY position` 은 테스트로 지킬 수 없다

M5 함정 표의 첫 줄인데, **테스트가 못 잡는다.** 지우고 돌려도 14건 전부 통과했다.

행을 일부러 뒤섞어 넣어도 통과했다. 실행 계획을 재 봤다:

```
SEARCH r USING INDEX sqlite_autoindex_search_result_1 (queryKey=? AND page=?)
SEARCH s USING INDEX sqlite_autoindex_campsite_summary_1 (contentId=?)
```

복합 PK 가 `(queryKey, page, position)` 이라 그 자동 인덱스를 훑으면 **우연히 position 순서로 나온다.**
즉 지금 순서가 맞는 것은 **PK 컬럼 순서 덕이지 우리가 요구했기 때문이 아니다.**

`ORDER BY` 는 그대로 뒀다. SQL 은 그것 없이 어떤 순서도 약속하지 않고,
PK 순서를 바꾸거나 인덱스를 더하거나 플래너가 다른 계획을 고르면 조용히 어긋난다.

> **테스트가 지켜 주지 못하는 불변식이 있다는 것을 아는 편이,
> 지켜 준다고 믿는 것보다 낫다.** DAO 주석에 실행 계획을 실측값으로 남겨 뒀다.

### 8.4 통과하는 테스트가 아무것도 안 지키고 있었다 (두 번째)

"나이는 받은 시각이지 연 시각이 아니다" 를 검증하는 테스트를 썼는데,
픽스처에 `cachedAt == lastAccessedAt` 을 심어 뒀다. **두 값이 같으니 무엇을 쓰든 통과한다.**

일부러 `fetchedAt = cached.lastAccessedAt` 로 바꿔 보고서야 알았다. 변이가 통과한 것이다.
픽스처를 "열흘 전에 받아서 오늘 다시 연 캠핑장" 으로 고치니 잡힌다 —
그리고 그 상황이야말로 현장에서 가장 흔하다.

백엔드 M7 의 `원본_보관` 테스트와 **똑같은 실패다.**

> 통과하는 테스트가 있다는 것과, 그 테스트가 무언가를 지킨다는 것은 다르다.
> 확인하는 방법은 하나뿐이다 — **일부러 깨뜨려 보고 빨개지는지 본다.**

### 8.5 코루틴이 예외를 복사해서 `suppressed` 가 사라졌다

`addSuppressed` 를 검증하는 테스트가 실패했다. 원인을 재 봤다:

```
thrown=IOException suppressed=0 cause=IOException causeSuppressed=1
```

`withContext(Dispatchers.IO)` 경계를 넘을 때 코루틴의 **스택트레이스 복구**가 예외를 복사한다.
복사본은 suppressed 를 옮기지 않고 원본을 `cause` 로 단다. 기록이 사라진 게 아니라 한 겹 아래로 내려간다.

복구는 환경에 따라 꺼질 수 있어 어느 쪽에 붙을지가 달라진다.
그래서 테스트는 **사슬 전체**를 훑는다 — 검증할 것은 "어디에 붙었나" 가 아니라 "남았나" 다.

### 8.6 판단이 필요했던 것 — `Json` 의 엄격성

`Converters` 와 `filterJson` 이 둘 다 기본 `Json`(`ignoreUnknownKeys = false`)이었다.
같은 문제로 보였지만 **성격이 다르다.**

| | 무엇이 지켜 주나 | 결정 |
|---|---|---|
| `Converters` (엔티티 컬럼) | **DB 스키마 버전.** 모양이 바뀌면 파괴적 마이그레이션이 테이블을 버린다 | 엄격 유지 |
| `filter_options.payload` | **아무것도.** 그냥 TEXT 한 칸이라 버전 추적 대상이 아니다 | `ignoreUnknownKeys = true` |

`payload` 는 **구버전이 쓴 JSON 을 신버전이 읽는 일이 실제로 생긴다.**
`FilterOptionDto` 에서 필드를 하나 빼고 배포하면 정확히 오프라인에서만 필터 시트가 무너진다.

`Converters` 의 원래 주석("우리가 쓰고 우리가 읽는 값이라 관대할 필요가 없다")은
같은 버전 안에서는 맞다. 그 전제가 성립하지 않는 쪽만 풀었다.

## 9. 남긴 것

- **즐겨찾기 없음.** 이번 범위에서 뺐다. 넣는 순간 D5(파괴적 마이그레이션)가 무효가 된다
- **선제 캐싱 없음.** 즐겨찾기를 넣으면 "즐겨찾기한 곳의 상세를 즉시 받아 둔다"가 자연스럽다.
  현장에서 필요한 것이 정확히 그것이다
- **캐시 용량을 사용자에게 보여주지 않는다.** 설정 화면 자체가 없다
- **`ORDER BY position` 을 지키는 테스트가 없다.** 8.3 참고. 실행 계획이 바뀌면 조용히 깨진다
- **비행기 모드 실기기 검증이 남았다.** DAO 와 폴백 규칙은 덮었지만
  화면 전체 흐름(배너·빈 상태 문구·필터 시트)은 아직 사람이 봐야 한다 (6번 체크리스트)
- **`CacheNotice.ageDays` 는 이미 안전했다.** 기기 시계를 되돌려도 음수가 되지 않는다 —
  `Cached.ageMillis` 가 `coerceAtLeast(0)` 을 걸어 둔다. 확인만 하고 고치지 않았다
